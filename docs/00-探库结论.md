## 2. 进程模型

```
com.vivo.health            主进程，数据库在这里打开
com.vivo.health.permanent  常驻进程
com.vivo.health.deviceConn 设备连接进程（蓝牙通道）
```

三个进程名是**点号形式**，不是 `:子进程` 形式，但属于**同一个 APK、同一个 UID**。
→ LSPosed 作用域勾 `com.vivo.health` 理论上覆盖三个进程，M1 需实测确认。

## 4. 加密体系（只记录，不处理）

进程内已加载：`libsqlcipher.so`、`libvivoseckey.so`、`libcpc_core_0.1.6.so`、`libvivo_cpc.so`、`libmmkv.so`。

## 5. 取库路径（已验证可行，M2 的核心）

vivo 用的是 `net.sqlcipher.database.SQLiteDatabase`，它有一个**静态字段**：

```java
sActiveDatabases : java.util.WeakHashMap<SQLiteDatabase, Object>
```

实测该表里有 5 个活跃实例，其中两个就是 `cc_health_*.db`。
读 `mPath` 字段就能识别是哪个库。

这比 OHSync 的「hook openDatabase + 反射单例 + 主动触发开库」三路兜底更直接：

1. **主路径**：反射读 `sActiveDatabases`，按 `mPath` 过滤 `cc_health_` → 拿到现成句柄
2. **兜底**：hook `SqlcipherSingleDbHelper.getWritableDatabase()`（vivo 自己的封装类
   `com.vivo.vcodeimpl.db.sqlcipher.single.SqlcipherSingleDbHelper`，有 `getDBName()`）
3. **再兜底**：hook `SQLiteDatabase.openDatabase` 的 `(String, String, CursorFactory, int)` 重载

两条实现上的坑（已踩过）：

- frida 调用 SQLCipher 对象的方法必须先 `Java.cast` 到具体类，否则 `rawQuery` / `moveToNext` 全是 `TypeError: not a function`
- `rawQuery` 返回的是 `net.sqlcipher.CrossProcessCursorWrapper`，必须 cast 到该类才能遍历

**关键发现（差点踩坑）**：`LIGHT_SLEEP_TIME` / `DEEP_SLEEP_TIME` / `REM_SLEEP_TIME` / `AWAKE_SLEEP_TIME` 存的是**段数，不是时长**。

实测某一晚（日期与数值已脱敏）：四个 `*_SLEEP_TIME` 列的值都只有个位数，
明显不是分钟数；改用四个 `*_SLEEP_LIST` 逐段解析 `enterTime/exitTime` 累加后，
四段时长之和**与 `EXIT_TIME - ENTER_TIME` 完全相等**，且与 App 界面显示的
总时长、深睡、浅睡、REM 逐项一致 ✅。

由此定案：分段时长一律从 `*_SLEEP_LIST` 累加，`*_SLEEP_TIME` 只当段数用。

四个分段列表首尾相接、无缝无重叠，可直接构成 HC 的 `stages`。
`ZONE_OFFSET=480`（分钟，UTC+8）。

## 7. 三个必须先解决的数据一致性问题

### 7.1 步数有三套，互不相等

实测连续四天，三套口径互不相等（具体数值已脱敏）：
分钟表求和 < `DATE_STEP_COUNT_BEAN` < 手机 `step-db`，且差值每天不同。
`DATE_*` 是 App 界面显示的"官方日汇总"，**需要你确认界面数字**，
才能决定写哪一套（详见映射草案 §6）。

### 7.2 心率数据量

601 天 × 约 5500 点 = 约 330 万点。按 3 个月回填 = 约 50 万点。
不能一点一条 record，必须分块聚合（详见映射草案 §5）。

### 7.3 运动类型枚举无中文名

`TYPE` 是私有整数，App 内没有可读映射表落在库里。**只能靠你在界面上看运动记录名称 + 时间，我按时间对账**。

## 8. vivo 与 OPPO（OHSync）的实现差异

| 维度 | OPPO | vivo | 影响 |
|---|---|---|---|
| 库所在进程 | 独立包 `com.heytap.databaseengineservice` | 主进程 `com.vivo.health` | vico 省事，不用跨包 |
| 取库方式 | hook openDB + 反射单例 + 主动触发 | **静态 `sActiveDatabases` 直接拿** | 更稳，可省掉重试轮询 |
| ORM | Room | GreenDAO + Room（step-db） | 表名规则不同，关键词表要重写 |
| 步数粒度 | 日级/小时级 | **分钟级（60s 一片）** | 写入质量更高 |
| 心率 | 点表 | **单列 JSON 数组**，每天一行 | 需解析 JSON，数据量更大 |
| 睡眠 | 单一 `type` 枚举（0/2/3/4） | **四个独立分段列表**，语义自明 | 不需要枚举对账，比 OPPO 简单 |
| 睡眠 TIME 字段 | — | **是段数不是时长** | 唯一一个坑，已排掉 |
| 明文库 | 无 | `step-db` 明文可直读 | 步数可作为交叉校验源 |
