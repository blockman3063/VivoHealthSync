# M2 读取端打通（不写 Health Connect）

> **公开仓库说明**：验收用的真实健康统计数值（累计步数、点数、日期范围等）已脱敏，
> 只保留「逐项一致」的结论与可对账的方法。

## 这一阶段要证明什么

「注入 → 取库 → 查表 → 跨进程回传 → 界面显示」这条链路真的通。

**本阶段不写 Health Connect**：映射未定稿就写，只会往 HC 里灌脏数据。

## 链路

```
VHSync 界面「读取预览」
   └─ TriggerSender.preview()  ──广播(带口令)──▶  com.vivo.health 进程内
                                                   SyncTrigger 收到 PREVIEW
                                                    └─ PreviewReader.collect()
                                                         ├─ SELECT ... FROM DATE_STEP_COUNT_BEAN
                                                         └─ SELECT ... FROM WATCH_HEART_RATE
                                                   RemoteConfig.pushPreview()
   ◀──contentResolver.call("preview")── SyncReceiverProvider
                                          └─ BridgeHandler.call() → PreviewStore
   PreviewStore.snapshot(StateFlow) → Compose 重组 → 卡片显示
```

口令校验在两端各做一次：广播里带 token（`SyncTrigger` 校验），provider 调用 arg 也带 token（`BridgeHandler` 校验）。
provider 不通时退回 `BridgeService` 显式绑定，与 OHSync 原设计一致。

## 实测确认的源数据格式

`WATCH_HEART_RATE.POINT_LIST` 的真实结构（探库时只知道是「JSON」，这次看清了）：

```json
[{"timestamp":<毫秒时间戳>,"value":<bpm>},{"timestamp":<毫秒时间戳>,"value":<bpm>}, ...]
```

- 一条 `_id` = 当天 00:00 毫秒，`POINT_LIST` 是**当天全部心率点**
- 单条约 20 万字符 / 数千点 → 全天逐条解析没有意义，预览只解析最近 1 条
- 点间隔中位 6 秒，与探库结论一致

`DATE_STEP_COUNT_BEAN`：`_id` = 当天 00:00 毫秒，`VALUE` = 全天步数，一天一行。

## 验收（真实数据对账）

界面显示 vs 直接查库（frida 在 vivo 健康进程内 `rawQuery`），逐项比对：

| 项 | 界面显示 | 直接查库 | 一致 |
| --- | --- | --- | --- |
| 步数天数 | N 天 | `COUNT(*)` | ✓ |
| 步数合计 | Σ 步 | `SUM(VALUE)` | ✓ |
| 步数起点 | 起始日 | `MIN(_id)` | ✓ |
| 步数终点 | 当天 | `MAX(_id)` | ✓ |
| 心率天数 | M 天 | `COUNT(*)` | ✓ |
| 心率范围 | 与步数相同的上下界 | `MIN/MAX(_id)` | ✓ |
| 最近一天点数 | K 点（含首末时刻） | 解析最新一条 `POINT_LIST` | ✓ |

（各项具体数值已脱敏；探库时步数行数比验收时少 1，不是矛盾，是当天新增了一行。）

模块日志同时印证：

```
VHSyncTrigger: 收到事件：...action.PREVIEW
VHSyncPreview: 预览采集完成：步数 N 天，心率 M 天 / 最近一天 K 点
VHSyncBridge : preview accepted
VHSyncHook   : 预览回传成功
```

「读取端」状态点：首次打开界面时是灰的（那一刻 vivo 健康刚重启、事件通道还没注册），
重开一次界面后收到 PING 回执变正常。行为符合事件驱动设计，不需要轮询。

## 顺手修掉的设计问题

1. **多进程重复回话**：vivo 健康 4 个进程都被注入，全部注册事件通道就会收到 4 份结果。
   现在 `startEventChannel()` 里用 `Application.getProcessName()` 过滤，只有 `com.vivo.health` 回话，
   其余打印「非主进程，不回话」后直接退出。
2. **provider 与 BridgeService 各写一份 method 分支**：加一个 method 要改两处，迟早写歪。
   `SyncReceiverProvider.call()` 现在整体转发 `BridgeHandler.call()`，两条通道共用一份实现。

## 踩坑记录

- **模块 ClassLoader 看不到宿主的 `net.sqlcipher.*`**。frida 里必须用两个 loader 切换：
  找 `TableReader` 用模块 loader，拿 `Java.use("net.sqlcipher.database.SQLiteDatabase")` 换宿主 loader，
  再 `Java.cast` 才能 `rawQuery`。App 代码里没这个问题（`TableReader` 全程用 `Any` + 反射，正是为了避开它）。
- **adb 点击坐标**：截图是缩放图，按图算坐标会点空。用 `uiautomator dump` 取 `bounds` 才可靠
  （本机实际 1440×3168，截图只有 489×1085）。
- **logcat 仍然要用直播流**：`adb logcat -d` 在这台机器上抓不到模块日志，原因见 `02-M1-脚手架.md`。
