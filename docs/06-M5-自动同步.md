# M5 自动同步

> **状态：✅ 已实现，真机验证通过（2026-11-08）。**
> 目标：vivo 健康在跑的时候，**不用打开本应用**，数据一变就同步进 Health Connect。

---

## 1. 一条数据要走过什么

```
vivo 健康写库
   │  ① SQLCipher 写入口被 hook（不进数据流，只置一个时间戳）
   ▼
自动同步线程被叫醒
   │  ② 去抖：等 10 秒没有新写入再动手（一次运动可能连写几百行）
   ▼
给 8 张源表各算一个指纹
   │  ③ 指纹 = 行数 + 相关列文本总长度
   ▼
只有指纹变了的类型才去查库、才推送
   │  ④ 心率变了就只推心率，不把 9 类 229 条全走一遍
   ▼
主进程写 Health Connect（clientRecordId 覆盖写，幂等）
```

推送失败不丢状态：不清「待处理」标记、不推进指纹，30 秒后重试。
只有整批都成功，指纹才前进 —— 否则下一次会漏数据。

## 2. 为什么是「写信号 + 指纹」而不是纯轮询

| 方案 | 延迟 | 代价 | 结论 |
|---|---|---|---|
| 纯定时轮询（如每 60 秒查一次库） | 最长一个周期 | vivo 健康进程里持续查库，费电 | ❌ |
| 只挂写信号 | 几乎即时 | 任何一次写入都要算指纹，批量写会频繁触发 | ⚠️ 需要去抖 |
| **写信号 + 去抖 + 指纹**（采用） | ~10 秒 | 平时零查询 | ✅ |
| 只靠定时兜底 | 慢 | 低 | 作为兜底保留 |

**为什么必须先算指纹**：写信号只知道「有人写库了」，不知道写了哪张表。
SQLCipher 的 `SQLiteStatement.execute()` 拿到的是预编译语句，读不出表名；
硬要解析 SQL 文本又受 vivo 的写法变化影响。指纹比对比解析 SQL 稳得多，也便宜
（600 行的表一次 `COUNT + SUM(LENGTH)` 是毫秒级）。

**指纹为什么够用**：同时看「行数」和「列文本总长度」。
行数变 = 有新记录（新一天、新一次运动、新一晚睡眠）；
总长度变 = 已有行被改写（今天的步数在涨、心率点追加进 `POINT_LIST`）。
两者都不变而内容变了的情况，最多漏一次，下一笔写入仍会触发；人工点「立即同步」
永远走全量，可以兜回来。

## 3. 主进程必须活着

写入 Health Connect 只能用**本应用的进程**（HC 按包名/Uid 校验权限），
所以「vivo 健康里的读取端」和「写 HC 的主进程」是两个进程，必须让后者活着。

三道措施：

1. **前台服务**（`SyncService`，`specialUse` 类型）—— 让它不被回收；
   开机 `BOOT_COMPLETED` 自动启动（`Settings.keepAlive` 默认开）。
2. **电池优化白名单** —— 首次打开发起一次系统对话框（`KeepAlive`）。
   没拿到也不至于立刻失效，但系统可能更积极地把服务清掉。
3. **唤醒广播** —— 主进程万一不在了，推送前先把它叫起来：
   `ACTION_WAKE` 显式广播，12 秒窗口内**最多重发 3 次**（单次广播实测会被丢）。

被唤醒后进程会自己 `startForegroundService`，数据接口随即可用。

## 4. 验收中碰到的两个真问题

### 4.1 口令只存内存 → 自动同步死锁（已修）

原来的 `TokenHolder` 刻意只把口令留在内存：「不想往 vivo 健康的私有目录塞东西」。
后果是：主进程一被杀，读取端内存里的口令也没了，而唤醒广播需要口令校验 → 

```
没有口令 → 广播被拒 → 主进程起不来 → 拿不到口令 → ……
```

实测日志就是那一行：`还没有配对口令：请先打开一次 VHSync 完成授权`，
然后每 30 秒重试一次，永远推不出去。

**修法**：用**宿主进程自己的 Context** 把口令写进 `com.vivo.health` 的
SharedPreferences（`vhsync_hook.xml`）。里面只有一个 32 字节随机串，不含任何健康数据。
进程重启时先从这个文件恢复，再发唤醒广播。实测落盘 148 字节，恢复正常。

> 仍然存在的一次性前置条件：装完模块后**要打开一次 VHSync**（授权 HC 权限 +
> 生成口令）。之后就不需要再打开了。

### 4.2 进程名取不到会被误判成主进程（已修）

vivo 健康有 4 个进程都会被注入。原判定是
`if (pn != null && pn != MAIN) return false` —— `pn` 为 null 时会当成主进程，
于是设备进程/常驻进程也会去推送，同一批数据被写多遍。

**修法**：`getProcessName()` 拿不到就退回读 `/proc/self/cmdline`，两条路都失败才按主进程处理。
判定收敛到 `retryContext()` 一处，不再各个函数各判一次。

### 4.3 唤醒广播被 OriginOS 的「关联启动」拦下（ROM 行为，代码解决不了）

`adb install` 之后应用处于 `stopped=true`，系统会丢弃发给它的广播。加
`FLAG_INCLUDE_STOPPED_PACKAGES` 解决了这一层 —— 但解决不了下一层：

| 发起方 | 加 stopped 标志后能否拉起后台的 VHSync |
|---|---|
| `adb shell am broadcast --include-stopped-packages`（shell 特权） | ✅ 能 |
| **vivo 健康进程（普通应用，uid 10xxx）** | ❌ 不能，广播被拦，`VHSyncWake` 一条日志都没有 |

这是厂商对「A 应用拉起 B 应用」的管控（关联启动），不是代码问题：调试期用
shell 特权发广播总是成功，真机上由 vivo 健康发就静默失败。

**结论**：把「主进程被系统回收后能被广播重新拉起」当成**尽力而为**，不作为
同步链路的必要条件。真正保证同步的是下面这条 —— 只要 VHSync 主进程还活着
（前台服务 + 电池优化白名单），写 HC 就走 binder，不需要任何广播。
用户侧还需要在 OriginOS 设置里给 VHSync 开「自启动」与「后台运行」，应用内
文案已注明。

## 5. 与 M4 的接口变化

| 位置 | 变化 |
|---|---|
| `QueryPlan.forTables(reader, only)` | 新增 `only: Set<RecordType>?`；null = 全量，否则只构建这些类型 |
| `Pusher.push(reader, only)` | 参数从 `incremental: Boolean` 改成 `only: Set<RecordType>?`；**返回 Boolean**（是否全批成功） |
| `Pusher.ensureHostReady()` | 12 秒窗口内重发唤醒广播，最多 3 次 |
| `Pusher` 回报 | 只有全部成功才调 `reportSyncDone`，避免增量窗口被错误推进 |
| `hook/ChangeDetector.kt` | 新增：表 → 类型映射 + 指纹 |
| `hook/WriteWatcher.kt` | 新增：SQLCipher 写入口信号（13 个数据库方法 + 3 个语句方法） |
| `hook/TokenHolder.kt` | 口令持久化到宿主私有目录 |
| `core/KeepAlive.kt` | 新增：电池优化豁免 |
| `hook/SleepBuilder.kt` | **删除**（OPPO 版死代码，M4 起就不该用） |
| `HookCoordinator.startSyncScheduler()` | 用新的 `startAutoSync()` 取代，原来的死代码删除 |

### 6.1 按变化增量推送的端到端证据

**前提**：全程没有打开 VHSync，vivo 健康停在前台。

操作：在 vivo 健康里手动记一条体重（64.2 公斤，15:50:58 保存）。

hook 侧日志（去抖窗口 10 秒到点即动）：

```
15:51:09.927 I/VHSyncChange: 检测到变化的类型：体重, 身高
15:51:09.927 I/VHSyncHook:   准备推送 2 类：体重, 身高（按变化）
15:51:09.940 I/VHSyncPush:   发送 weight：2 条，201 字节
15:51:09.941 I/VHSyncPush:   发送 height：2 条，205 字节
15:51:09.941 I/VHSyncPush:   推送完成，共 4 条（2 类）
```

Health Connect 库侧版本快照（前后各拉一次，对比 `client_record_version`）：

| 类型 | 行数 A→B | 最大版本 | 结论 |
|---|---|---|---|
| steps | 2→2 | 没变 | 未变化 |
| heart_rate | 144→144 | 没变 | 未变化 |
| distance | 2→2 | 没变 | 未变化 |
| active_calories | 2→2 | 没变 | 未变化 |
| sleep_session | 29→29 | 没变 | 未变化 |
| blood_oxygen | 8→8 | 没变 | 未变化 |
| **weight** | **1→2** | **变了** | 有变化 |
| **height** | **1→2** | **变了** | 有变化 |
| exercise_session | 47→47 | 没变 | 未变化 |

为什么身高也动了：`WEIGHT_BEAN` 一张表同时承载体重和身高，指纹是**按表**算的，
所以这一族里的类型会一起被判定为「变了」。这是设计取舍（宁可多推一类，不做
漏推），代价是多一次幂等覆盖写。

> 注：vivo 健康进程的日志刷得极快，logd 的 chatty 限流会丢掉我们的一部分日志。
> 判断「到底同步了没有」不要只看日志，要看 Health Connect 库里 `client_record_version` 有没有动。

## 7. 已知限制

1. **首次仍需打开一次 VHSync**：HC 权限授权 + 口令生成。之后不再需要。
2. **系统级限制靠用户配合**：OriginOS 的「自启动」「后台运行」需要手动允许；
   应用内已申请电池优化豁免，但厂商的额外管控应用内改不了。
3. **vivo 健康完全没在跑时不推送**：读不到库。此时唤醒广播会在 vivo 健康下次启动时重新生效。
4. **指纹只覆盖 8 张表**：`TableRules` 里其它表（压力、鼾声等）按设计丢弃，不参与检测。
