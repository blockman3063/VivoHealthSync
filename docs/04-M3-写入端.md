## 2. 数据流（M3）

```
VHSync「立即同步」
  └─ TriggerSender.syncNow() ──广播(带 token)──▶ com.vivo.health 主进程
        SyncTrigger.ACTION_SYNC_NOW → HookCoordinator.pushNow()
          Pusher.push(reader)
            QueryPlan.forTables()  ← sqlite_master + PRAGMA 推导表/列
            reader.query(SELECT)   ← 只读，宿主已打开的 SQLCipher 实例
            步数：1 行 → 1 条 StepsRecord
            心率：1 行 POINT_LIST → N 段 HeartRateRecord
            PayloadCodec.encode() → 按 400 KB 分块
            ContentProvider.insert() / Bridge.insert() ── token ──▶ VHSync 主进程
  BridgeHandler.insert() → SyncEngine.consume()
    RecordMapper.map() → MetadataFactory.withClientId() 设 clientRecordId / version
    HcClient.writeAll() → Health Connect
```

只有 `com.vivo.health` 主进程回话（其余 3 个进程 M2 已排除）。写入只在主进程发生。

## 3. 映射落地要点

**步数**：`_id` 是当天 00:00 绝对毫秒 → `startTime`；`endTime = min(_id + 86400000, now)`，
避免 HC 拒收未来时间；`VALUE` → `count`；`sourceKey = vivo-step-{_id}`。
`endTime <= startTime` 的当天行跳过。

**心率**：`POINT_LIST` 是 `[{"timestamp":ms,"value":bpm}]`。
按 `bucket = ts / 600000 * 600000` 分绝对 10 分钟桶，同桶相邻点间隔 > 5 分钟再切段，
单段硬上限 200 样本；同毫秒重复点先去重；`startTime/endTime` 取段内首末点
（单点段 end = start+1ms）；样本经 `sample_<i>_bpm` / `sample_<i>_at` 传输，
由 `RecordMapper.samples()` 还原。
`sourceKey = vivo-hr-{段首点ts}`。

**幂等**：`clientRecordId = "vhsync:" + type.id + ":" + sourceKey`，
`clientRecordVersion = System.currentTimeMillis()`。`vhsync:` 前缀从首次写入起**不能改**。

**窗口**：M3 固定只取最近 2 个本地自然日（含今天），全窗口回填与增量留给 M5。
下界按本地 00:00 对齐（`TimeZone.getDefault()`），不是简单的 `now - N*86400000`，
否则边界那行会被漏掉。

### 4.3 本轮唯一的真实阻塞：Android 11+ 包可见性

首轮真机同步全线失败，现象是 vivo 健康进程里调用本应用 provider 抛
`IllegalArgumentException: Unknown authority io.github.blockman3063.vhsync.sync`，
provider 兜底 `Bridge.insert()` 也返回 false，整批推送放弃。

排除过程（都不是原因）：HC 两项权限均已授予、HMA 未隐藏本应用、
目标进程未被冻结（`oom_score_adj=200`、`cached=false`）、provider 本身完好
（`adb shell content call` 能返回 config）、包确实可见（`getPackageInfo` 正常）、
设备已解锁。

`frida` 在 vivo 健康进程内直接对比两条调用路径，定位到差异：

```
pm.resolveContentProvider(authority, 0)  ->  ContentProviderInfo{name=...vhsync.sync}   ✅
ContentResolver.call(uri, "config", ...) ->  IllegalArgumentException: Unknown authority ❌
```

`resolve` 不带调用方 uid 时能解析，`call` 带 callingUid 时被 **AMS 的 `AppsFilter`**
过滤掉了。根因是 Android 11+ 的包可见性：调用方（`com.vivo.health`）没在
`<queries>` 里声明本应用，跨应用组件解析就被判定为不可见。

**`QUERY_ALL_PACKAGES` 救不了** —— 它只影响「列出已安装应用」，不改变
`filterAppAccess` 对跨应用组件访问的判断。这一点很容易误判。

修复：被访问方声明 `android:forceQueryable="true"`。`AppsFilter.shouldFilterApplication`
里 `mForceQueryable` 命中被查询 uid 时直接放行。改完立即成功。

代价：本应用对其它应用「可见」。评估过，不是新增攻击面 —— 本应用本来就 export
了 provider 与 bridge service，两者都带一次性口令校验。

### 5.7 失败分支

| 现象 | 处理 |
|---|---|
| `源库结构对不上，本次推送整体放弃` | 按约定停下报告，比对实际列名与 docs/00 探库结论，不猜、不吞错 |
| 推送 0 条 | 查 `VHSyncPlan` 窗口下界与源表 `_id` 单位（应为当天 00:00 毫秒） |
| `provider 与 Bridge 都不通` | 查 HMA：`adb logcat -s AppsFilter` 是否有 `vhsync -> com.vivo.health BLOCKED` |
| HC 报 `SecurityException` | 覆盖安装撤销了权限，回 5.1 重新授权 |
| HC 拒收记录（`IllegalArgumentException`） | 查 endTime 是否落在未来、samples 是否越界、是否 `start == end` |
| `clientRecordId` 里出现 `ohsync:` | 旧数据残留，用 App 内「清除本应用已写入的数据」清干净再重同步 |
| 记录数翻倍 | 查 `MetadataFactory.withClientId()` 是否真的设了 `clientRecordId`、HC 版本语义 |
| `TransactionTooLargeException` / 推送批次失败 | 调小 `Pusher.MAX_PAYLOAD_BYTES`（当前 400 KB）再编译安装；分批是按编码后字节数切的，心率单条可达 20 KB |
| 写入了窗口外的日期 | 查源表 `_id` / `VALUE` 的列类型；SQL 已用 `CAST(... AS INTEGER/REAL)` 规避 SQLite 的 TEXT 比较陷阱 |

## 7. M5 方向修正（用户 2026-11-08 提出，待确认后实施）

用户指出：既然有 root + LSPosed，模块应当做到「**打开 vivo 健康就具备同步能力**」，
而不是要求 vivo 健康和 VHSync 同时运行。这个诉求成立，但实现路径要分清。

### 7.1 判定表

| 想法 | 判定 | 理由 |
|---|---|---|
| 在 vivo 健康进程里直接写 HC | ❌ 不可行 | HC 按调用方 UID 校验 `WRITE_*`，注入端 UID 是 `com.vivo.health`，未授权 |
| root 直改 `healthconnect.db` 绕过权限 | ❌ **不做** | HC 私有库有 WAL、索引、变更通知、`clientRecordId` 去重与权限记录；直接写会写坏系统数据，且格式随 HC 版本变 |
| root 一次性解除厂商后台限制 | ✅ 该用在这 | 让框架原生的「按需拉起主进程」恢复，运行时角色不变 |
| 注入端取库成功后自动触发同步 | ✅ 该做 | M3 为验收暂时关掉了自动推送 |
| 显式 `bindService` 优先于 provider | ✅ 待实测 | `BridgeService` 已 exported 且只放行 vivo 健康；从前台应用 `bindService(BIND_AUTO_CREATE)` 可拉起目标进程，不受后台启动服务限制 |

### 7.2 真正的瓶颈

M1/M2 实测：ColorOS 不会因为「别的进程访问 provider」就启动已退出的 VHSync；
广播与闹钟也拉不起 cached 进程（见 `WakeReceiver` / `SyncService` 的实测注释）。
OHSync 因此用前台服务常驻兜底，代价是常驻进程与一条通知。

**M3 验收时又撞到一次，有日志为证**：VHSync 主进程被系统回收后，注入端收到
`SYNC_NOW`，发出 `ACTION_WAKE` 唤醒广播，12 秒轮询到期仍未就绪，只能放弃：
```
I/VHSyncTrigger: 收到事件：...action.SYNC_NOW
I/VHSyncPush:    主进程不在，发唤醒广播
E/VHSyncPush:    主进程未就绪，本次推送放弃（下轮会重试）
```
手动 `am start` 打开界面后立刻成功。这说明**唤醒广播是死路**，M5 必须换机制
（`bindService` 或前台服务二选一，不能靠广播）。

**不是架构要求两个 App 同时开**：装完打开过一次之后，前台服务本就常驻；
M3 另外把自动推送关掉了，才变成必须手动点「立即同步」。

### 7.3 M5 拟改为

1. 注入端在取库成功后立刻发一次**增量**同步（不做全窗口灌数据，避免 HC 限流）
2. IPC 顺序改为 `Bridge(bindService)` 优先 → provider 兜底，利用 vivo 健康在前台时拉起写入端
3. root 只做安装时的一次性配置：deviceidle 白名单、appops 允许后台活动、清 stopped 状态；
   运行时**不发 `su`、不碰 HC 库**
4. 前台服务降级为可选（「保持后台运行」默认关），不再作为同步的前提
5. 每条都要真机实测，尤其是 `bindService` 能否在 ColorOS 上把进程拉起来

### 7.4 边界

M3 验收基线**不变**：手动「立即同步」写对 + 幂等成立。
上述改动在 M3 通过后再进 M5，避免验收时混入未验证的架构变更，
也避免 Health Connect 权限因反复覆盖安装被反复撤销。
