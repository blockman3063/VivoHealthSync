# 映射设计草案（待确认）

> 依据：`docs/00-探库结论.md` 与本机的表结构清单（`.probe/`，不随仓库上传）
> 原则：只读源库；每类数据写入前先过一遍「单位 + 时间戳 + 枚举」三关；HC 无对应类型的按设计丢弃并在 App 内明示。
> **公开仓库说明**：用于界面/库对账的个人健康测量值已替换成相对描述，映射规则与结论不变。

---

## 1. 总体约定

- 时间：源表全部是**毫秒**（列名已带 `_MS`，实测量级 1.79e12 确认）。
- 时区：HC 存 UTC 瞬时值，源数据本身就是绝对毫秒，**不需要**再加 `ZONE_OFFSET`；`ZONE_OFFSET=480` 只用于按天分桶（`date(ts/1000,'unixepoch','+8 hours')`）。
- 幂等：`clientRecordId` 用源数据主键构造，重复同步覆盖不新增。
- 增量：以 `START_TIMESTAMP_MS` / `_id` 为水位线，只推水位之后的数据。

## 2. 逐类映射表

### 步数 → `StepsRecord`

| 项 | 内容 |
|---|---|
| 源表 | **`DATE_STEP_COUNT_BEAN`（已定）** |
| 字段 | `_id`（当天 00:00 毫秒）→ startTime，次日 00:00 → endTime，`VALUE` → count |
| 幂等键 | `vivo-step-{_id}` |
| 当天处理 | 当天还没过完，endTime 取 `min(次日00:00, 现在)`，否则 HC 会拒收未来时间的记录；下次同步覆盖同一条 |
| 为什么不用分钟表 | 实测同一天，分钟表求和 < `DATE_` 日汇总 < 手机 `step-db`，三者互不相等（数值已脱敏）；**用户确认界面显示值与 `DATE_` 日汇总一致**。验收标准是「与 vivo 健康界面对得上」，所以以日汇总为准 |
| 为什么不用 step-db | 那是手机计步，与手表口径不同，且与界面数字有明显差值 |

### 距离 → `DistanceRecord`

| 项 | 内容 |
|---|---|
| 源表 | **`DATE_DISTANCE_BEAN`（日级，与步数同源同口径）** |
| 字段 | `VALUE`（米）→ `Length.meters(value)` |
| 幂等键 | `vivo-dist-{_id}` |

### 活动卡路里 → `ActiveCaloriesBurnedRecord`

| 项 | 内容 |
|---|---|
| 源表 | **`DATE_CALORIE_BEAN`（日级，单位已是 kcal）** |
| 字段 | `VALUE`（kcal）→ `Energy.kilocalories(value)` |
| 幂等键 | `vivo-cal-{_id}` |
| 备注 | 分钟表 `SPORT_TODAY_ACTIVITY__CALORIE` 的 VALUE 单位是 **cal**（需 /1000），但既然步数/距离都用日级，卡路里也统一用日级，避免三者在 HC 里日总量对不上 |

### 心率 → `HeartRateRecord`

| 项 | 内容 |
|---|---|
| 源表 | `WATCH_HEART_RATE`，`_id`=当天 00:00，`POINT_LIST` 是 JSON 数组 |
| 字段 | `[{timestamp, value}]` → samples |
| 分块 | **每 10 分钟一条 record**（约 100 个 sample），避免单条 record 过大 |
| 时间 | record 的 startTime/endTime 取块内首末样本时间 |
| 幂等键 | `vivo-hr-{块起始分钟毫秒}` |
| 数据量 | 90 天回填 ≈ 12960 条 record，可接受 |
| 备注 | 静息心率（`DAILY_REST_RATE_BEAN`）**不单独写**，HC 没有「静息心率记录」类型，混进普通心率会污染曲线；如需，后续可用 `RestingHeartRateRecord` 单独评估（该类型是日内单值，语义不完全一致） |

### 睡眠 → `SleepSessionRecord`（含 stages）

| 项 | 内容 |
|---|---|
| 源表 | `WATCH_SLEEP_BEAN`（`ENTER_TIME>0` 的 699 条） |
| session | `ENTER_TIME` → startTime，`EXIT_TIME` → endTime |
| stages | `LIGHT_SLEEP_LIST` → `STAGE_TYPE_LIGHT`；`DEEP_SLEEP_LIST` → `STAGE_TYPE_DEEP`；`REM_SLEEP_LIST` → `STAGE_TYPE_REM`；`AWAKE_SLEEP_LIST` → `STAGE_TYPE_AWAKE`。每个元素 `{enterTime, exitTime}` 就是一段 |
| 幂等键 | `vivo-sleep-{UUID}` |
| 已对账 | 实测一晚：四个分段列表累加的时长之和 = `EXIT_TIME - ENTER_TIME`，且与界面显示的总时长、深睡、浅睡、REM 逐项一致（具体数值已脱敏）✅ |
| 备注 | 四段列表首尾相接无空隙，stages 可完整覆盖 session。`SCORE`（睡眠评分）HC 无字段，丢弃 |

### 血氧 → `OxygenSaturationRecord`

| 项 | 内容 |
|---|---|
| 源表 | `WATCH_OXYGEN`（**仅 8 行**） |
| 字段 | `POINT_LIST[].value`（整数百分比，实测在合理生理区间内，具体数值已脱敏）→ **`Percentage(value/100.0)`** |
| 时间 | `POINT_LIST[].timestamp`（单点，非区间）→ start=end=timestamp |
| 幂等键 | `vivo-spo2-{timestamp}` |

### 血压 → **不实现**

| 项 | 内容 |
|---|---|
| 源表 | `WATCH_BLOOD_PRESSURE`（0 行） |
| 结论 | 用户确认**手表没有血压功能**，源表永远为空。不写读取分支、不申请 `WRITE_BLOOD_PRESSURE` 权限，避免在授权页里出现一个永远用不上的条目 |

### 体重 → `WeightRecord`

| 项 | 内容 |
|---|---|
| 源表 | `WEIGHT_BEAN`（1 行） |
| 字段 | `WEIGHT`（kg，数值已脱敏）→ `Mass.kilograms()`；`_id` 是毫秒时间戳 |
| 幂等键 | `vivo-weight-{_id}` |
| 备注 | `BODY_FAT` 无有效值，不写 `BodyFatRecord`；`HEIGHT` 可写 `HeightRecord`（可选） |

### 运动 → `ExerciseSessionRecord`

| 项 | 内容 |
|---|---|
| 源表 | `SPORT_RECORD_BY_WATCH_BEAN`（47 条） |
| 字段 | `RTC_START_TIME`/`RTC_END_TIME` → session 时间；`CALORIE`（kcal）；`DISTANCE`（米）；`AVERAGE_RATE`/`MAX_RATE` 可作为 `ExerciseSegment` 之外的附加 |
| 幂等键 | `vivo-ex-{TAG}`（`TAG` 是业务唯一 ID，比 `_id` 稳定） |
| type 映射 | 见 §4，未知一律 `EXERCISE_TYPE_OTHER` |
| 备注 | `TIME`（毫秒）与 `END-START` 一致，不用 |

## 3. 心率分块示意

```
一天 5500 点，间隔 6 秒
→ 每 600 秒切一块，块内 samples 全部塞进同一条 HeartRateRecord
→ record.startTime = 块内首个 sample.ts，endTime = 块内末个 sample.ts
→ clientRecordId = "vivo-hr-" + 块起点整分毫秒
```

断档（实测单日 14 处 >5 分钟）天然按块切开，不会把长间隔算进同一条 record。

## 6. 已确认结论（2026-11-07）

| 问题 | 结论 | 依据 |
|---|---|---|
| 步数口径 | **用 `DATE_STEP_COUNT_BEAN`** | 界面显示值与 `DATE_` 日汇总一致（仅有采集时点造成的小差值），具体数值已脱敏 |
| 睡眠对账 | **完全一致，无需调整** | 界面的总时长 / 深睡 / 浅睡 / REM 四项，与四个分段列表逐段累加结果逐项相等 |
| 运动类型 | 6 种已对上，5 种降级 OTHER | 见 §4 |
| 血压 | **不实现** | 手表无此功能 |
| 血氧 | 照实写入（历史天数很少） | 界面显示的「上次测量日期」与库内最后一条一致；未开连续血氧 |

运动记录页的四项累计与库内求和全等，说明 `SPORT_RECORD_BY_WATCH_BEAN` 就是界面数据源，映射口径可靠。
