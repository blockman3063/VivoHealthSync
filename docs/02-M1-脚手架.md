## 排查记录：一次误判的复盘（重要）

**错误结论**：以为 LSPosed 没有加载模块。理由有两条，两条都不成立。

| 当时的判据 | 为什么无效 |
| --- | --- |
| `grep -c vhsync /proc/<pid>/maps` = 0 | LSPosed 用 `LspModuleClassLoader` + `InMemoryDexFile` 加载模块，模块 APK 不进 maps。对照 `systemui`（colorduo 正常注入）同样是 0，两边完全一样 |
| `adb logcat -d \| grep VHSyncHook` 为空 | vivo 健康日志量极大（实测 45 秒 38662 行），`logcat -d` 是快照，模块日志要么被缓冲区淘汰、要么被 logd 限流丢掉。**抓模块日志必须开直播流** `adb logcat > file`，不能用 `-d` 事后抓 |

**证伪方式**：frida 附着到 `com.vivo.health`，`Java.enumerateLoadedClassesSync()` 里
`io.github.blockman3063.vhsync.hook.*` 共 30 个类已加载；再用 `enumerateClassLoadersSync()`
找到 `LspModuleClassLoader`，`Java.choose` 拿到 `VHSyncEntry` / `HookCoordinator` / `DbAccess` 实例。

**顺带记下的坑**：`Java.use` 用的是 App 的 ClassLoader，找不到模块类；
必须先遍历 ClassLoader 找到能 `loadClass` 模块入口类的那个，再 `Java.classFactory.loader = it`。

### 本轮修掉的两个真 bug

1. **Context 永远拿不到**。`onPackageReady` 被调用时 `ActivityThread.currentApplication()` 还是 `null`，
   原代码只调一次 `AppContextHolder.init()` 就放弃，`context` 永远是 null。
   → 改为后台线程重试（2 秒 × 15 次），实测**第 1 次重试即成功**。
2. **首个数据库句柄可能丢失**。`onDatabaseReady` 原本只在 `onPackageReady` 里绑定，
   如果 hook 在绑定前就回传了实例，句柄被丢弃。
   → 改为 `bindDatabaseCallback()` 幂等绑定，`onPackageLoaded` 也调用一次。

同时给 `onPackageReady` 加了进程名日志（`Application.getProcessName()`），多进程问题由此暴露。
