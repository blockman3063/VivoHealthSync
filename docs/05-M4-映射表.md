|---|---|---|---|---|---|
| 1 | 距离 | `DATE_DISTANCE_BEAN` | `DistanceRecord` | 每个自然日 1 条 | 近 2 天（与步数同窗口） |

## 2. 距离（`DATE_DISTANCE_BEAN`）

**结构**：`_id:INTEGER` + `VALUE:REAL`，与 `DATE_STEP_COUNT_BEAN` 完全同构。

| 源 | HC `DistanceRecord` |
|---|---|
| `_id`（本地 00:00 的绝对毫秒） | `startTime` |
| `min(_id + 86400000, now)` | `endTime` |
| `VALUE`（米） | `Distance(meters = VALUE)` |
| — | `startZoneOffset` / `endZoneOffset` = 本地时区 |

**单位实测**：`dist / steps` 比值稳定在 0.77 ~ 0.80（米/步）。同时 App 首页
「距离 0.94 公里」与表里当天的 945 完全对应 —— **单位是米，不需要换算**。

**过滤**：`VALUE <= 0` 跳过（当天没走路就没有这条记录的意义）。

**幂等键**：`vhsync:distance:vivo-dist-{_id}`

---

## 3. 卡路里（`DATE_CALORIE_BEAN`）

**结构**：同距离表，`VALUE:REAL`。

| 源 | HC `ActiveCaloriesBurnedRecord` |
|---|---|
| `_id` | `startTime` |
| `min(_id + 86400000, now)` | `endTime` |
| `VALUE`（千卡） | `Energy(kilocalories = VALUE)` |

**「活动消耗」而不是「总消耗」的依据**（这一点很关键，写错就会把基础代谢重复计入）：

1. 表值与 App 首页「热量 / 400 千卡」那个数字逐日一致（实测同一天两处完全相同）。
2. 若它是总消耗，以这个量级反推基础代谢会只剩个位数千卡，不可能。
3. App 的「热量」目标是 400 千卡，这是活动消耗目标的量级，总消耗目标不会设这么低。

**过滤**：`VALUE <= 0` 跳过。

**幂等键**：`vhsync:active_calories:vivo-cal-{_id}`

## 4. 睡眠（`WATCH_SLEEP_BEAN`）—— 最需要确认的一类

**结构**（40 列，只取用得上的）：

| 列 | 含义 | 实测 |
|---|---|---|
| `UUID` | 主键，701 行 701 个不同值 | 无重复 |
| `ENTER_TIME` / `EXIT_TIME` | 整段睡眠的起止 | 绝对毫秒 |
| `ZONE_OFFSET` | 时区分钟数 | 固定 480（+08:00） |
| `LIGHT_SLEEP_LIST` / `DEEP_SLEEP_LIST` / `REM_SLEEP_LIST` / `AWAKE_SLEEP_LIST` | 分段列表 | JSON 数组，元素 `{customerId, enterTime, exitTime}`，**绝对毫秒** |
| `LIGHT_SLEEP_TIME` 等四个 | **是分段条数，不是时长** | 见下 |

**`*_SLEEP_TIME` 是条数，这一点必须记牢**：三晚实测，`LIGHT_SLEEP_TIME` = 12/11/9，
而对应 `LIGHT_SLEEP_LIST` 的段数正好也是 12/11/9。若按「时长」解读会得到「一晚浅睡 12 分钟」这种荒谬结果。
真实时长只能由分段自己累加。

**分段完整性实测**（三晚全查）：

| 检查项 | 结果 |
|---|---|
| 四类分段累加 vs `EXIT-ENTER` | 100.0% / 100.0% / 100.0% |
| 相邻段重叠 | 0 |
| 相邻段间隙 | 0 |
| 越界段（超出 ENTER..EXIT） | 0 |
| 首段起点距 ENTER / 末段终点距 EXIT | 0.0 分钟 / 0.0 分钟 |

即：vivo 的分段是对整个睡眠区间的**无缝无重叠完整切分**。这意味着可以放心地
一条 `SleepSessionRecord` 装全部 stages，不需要补齐空档。

**映射**：

| 源 | HC |
|---|---|
| `ENTER_TIME` | `startTime` |
| `EXIT_TIME` | `endTime` |
| `ZONE_OFFSET * 60` | `ZoneOffset.ofTotalSeconds(...)` |
| `LIGHT_SLEEP_LIST[i]` | `Stage(enter, exit, STAGE_TYPE_LIGHT)` |
| `DEEP_SLEEP_LIST[i]` | `STAGE_TYPE_DEEP` |
| `REM_SLEEP_LIST[i]` | `STAGE_TYPE_REM` |
| `AWAKE_SLEEP_LIST[i]` | `STAGE_TYPE_AWAKE` |
| `UUID` | `clientRecordId` 的 sourceKey |

HC 1.1.0 的 `SleepSessionRecord` 有 7 个 stage 常量
（`UNKNOWN / AWAKE / SLEEPING / OUT_OF_BED / LIGHT / DEEP / REM / AWAKE_IN_BED`），
vivo 的四类正好一一对应，不需要降级。

**数据质量（实测，701 行）**：

| 情况 | 条数 | 处理 |
|---|---|---|
| 坏行（`ENTER_TIME <= 0` 或 `EXIT_TIME <= ENTER_TIME`） | **2** | 跳过，不写 |
| 时长 < 1 小时 | 157 | **建议保留**（见下方决策点） |
| 1 ~ 3 小时 | 53 | 保留 |
| 3 ~ 6 小时 | 111 | 保留 |
| > 6 小时 | 378 | 保留 |

短睡眠抽查：都是白天时段（如 13:07→13:53），即**午睡**，不是脏数据。
最近 8 晚每晚 1 条主睡眠（仅 11-03 是「主睡眠 + 午睡」两条）。

**幂等键**：`vhsync:sleep_session:vivo-sleep-{ENTER_TIME}`

> 用 `ENTER_TIME`，不用 `UUID`。理由：UUID 属于设备侧，手表重置/换表后可能重建，
> 而「同一晚的入睡时刻」在业务上唯一且稳定。二者对同一段睡眠一一对应，实测无冲突。

## 5. 血氧（`WATCH_OXYGEN`）

**结构**：`_id:INTEGER`（当天 00:00）、`POINT_LIST:TEXT`、`IS_UPLOADED`、`SOURCE_FROM`。

**实测**：全表只有 8 行，且**每行 POINT_LIST 里只有 1 个点**。点的字段是
`{"timestamp": 绝对毫秒, "value": 95~98, "highAltitude": 0}`。

所以实际粒度是「每次测量 1 个点」，而不是心率那种「一天一列点」。

| 源 | HC `OxygenSaturationRecord` |
|---|---|
| `point.timestamp` | `time` |
| `point.value`（0-100） | `Percentage(value)` |
| 本地时区 | `zoneOffset` |

**单位**：`Percentage` 接受 0-100 的 double，vivo 的值域正好是 95~98，直接传，不除 100。
`highAltitude` 恒为 0，HC 没有对应字段，**按设计丢弃**。

**旁证**：最新一条是 2026-01-25、值 96%，与 App 首页「血氧饱和度 1/25 96%」完全一致。

**幂等键**：`vhsync:blood_oxygen:vivo-spo2-{timestamp}`

## 6. 体重（`WEIGHT_BEAN`）

**结构**（7 列）：`_id:INTEGER`（测量时刻，绝对毫秒）、`WEIGHT:REAL`、`BODY_FAT:REAL`、
`HEIGHT:INTEGER`、`VERSION`、`IS_UPLOAD`、`IS_DELETE`。

**实测**：全表 1 行。`WEIGHT` 是 kg 量级（64）、`HEIGHT` 是 cm 量级（177）、
`BODY_FAT` 为 **0**（表示未测，不是 0% 体脂）。

| 源 | HC |
|---|---|
| `_id` → `time` | `WeightRecord(time, zoneOffset, Mass(kilograms = WEIGHT), meta)` |
| `HEIGHT` | `HeightRecord(time, zoneOffset, Length(meters = HEIGHT / 100.0), meta)` |
| `BODY_FAT == 0` | **跳过**，不写 `BodyFatRecord`（0 不是有效体脂率，HC 也会拒收） |

**幂等键**：`vhsync:weight:vivo-weight-{_id}` / `vhsync:height:vivo-height-{_id}`

> 身高是否要写，见决策点 4。

## 7. 运动（`SPORT_RECORD_BY_WATCH_BEAN`）

**结构**（177 列，只取关键列）：

| 列 | 含义 | 实测 |
|---|---|---|
| `_id` | 自增主键 | 1 ~ 47 |
| `TYPE` | 运动类型**编码** | 见下 |
| `RTC_START_TIME` / `RTC_END_TIME` | 起止 | 绝对毫秒 |
| `TIME` | 时长 | **毫秒**（与 `END-START` 差 0.2% 以内） |
| `CALORIE` / `DYNAMIC_CALORIE` | 卡路里 | 千卡 |
| `DISTANCE` | 距离 | **米**（`INTEGER`，无小数的原因见下） |
| `AVERAGE_RATE` / `MAX_RATE` / `MIN_RATE` | 运动心率 | bpm |
| `SWIM_TYPE` | 泳姿子类型 | 仅游泳有值 |

### 7.1 TYPE 枚举 —— 47 条逐条对账得出，不是猜的

做法：把 App「运动记录」列表全部 47 条（滚动采集）的**显示名称 + 时间**，
与库里的 `TYPE + RTC_START_TIME` 按分钟对齐。结果：47/47 全部匹配，
且同一 `TYPE` 反复出现时名称始终一致，**零冲突**。

| TYPE | App 显示名 | 出现次数 | → HC `EXERCISE_TYPE_*` |
|---|---|---|---|
| 2 | 户外跑步 | 3 | `RUNNING` (56) |
| 4 | 户外骑行 | 5 | `BIKING` (8) |
| 5 | 泳池游泳 | 10 | `SWIMMING_POOL` (74) |
| 10 | 自由训练 | 18 | **待定**，见决策点 1 |
| 12 | 户外步行 | 2 | `WALKING` (79) |
| 13 | 健身课程 | 1 | `EXERCISE_CLASS` (26) |
| 20 | 划船机 | 1 | `ROWING_MACHINE` (54) |
| 28 | 羽毛球 | 2 | `BADMINTON` (2) |
| 30 | 乒乓球 | 1 | `TABLE_TENNIS` (75) |
| 108 | 仰卧起坐 | 1 | **待定**，见决策点 2 |
| 114 | 操场跑步 | 3 | `RUNNING` (56) |

上表右边的常量名全部取自 `connect-client:1.1.0-api.jar` 的
`ExerciseSessionRecord` 反编译常量，不是凭文档记忆写的。

**未枚举到的 TYPE 一律降级为 `EXERCISE_TYPE_OTHER_WORKOUT` (0)**，
并在日志里打一次编码值，方便以后补表。

### 7.2 距离单位为什么是米

- 户外骑行：10080 米 / 73 分钟 ≈ 8.3 km/h，符合骑行；
- 户外跑步：5750 米 / 89 分钟 ≈ 3.9 km/h，符合慢跑；
- 泳池游泳：500 米 / 30 分钟 ≈ 1.0 km/h，符合游泳。

三条互相独立的记录都落在合理区间，**单位是米**。`DISTANCE` 声明为 INTEGER 是因为
vivo 在手表侧就取整到米，不是单位更粗。

### 7.3 映射

| 源 | HC `ExerciseSessionRecord` |
|---|---|
| `RTC_START_TIME` / `RTC_END_TIME` | `startTime` / `endTime` + 本地 zoneOffset |
| `TYPE` → 上表 | `exerciseType` |
| App 显示名（上表第二列） | `title` |
| `EID` | `clientRecordId` 的 sourceKey |

`segments` / `laps` / `route` 全部传空 —— M4 不写运动轨迹（见 §9）。

**幂等键**：`vhsync:exercise_session:vivo-sport-{EID}`

> 用 `EID`（设备侧唯一事件 ID）而不是 `_id`。`_id` 是本地自增，重建库会变；
> `EID` 实测 47 条全唯一。两者都唯一时优先用业务 ID。

### 7.4 运动里的距离/卡路里**不重复写**

`SPORT_RECORD_BY_WATCH_BEAN` 自带 `DISTANCE` / `CALORIE`，但**不写**成独立的
`DistanceRecord` / `ActiveCaloriesBurnedRecord`。原因：`DATE_DISTANCE_BEAN` /
`DATE_CALORIE_BEAN` 的日汇总已经包含这部分运动量，再写一遍会双重计入。
`ExerciseSessionRecord` 只承载「什么运动、什么时候、多久」。

（HC 里运动消耗与日汇总的正确关系是「运动记录 + 全天总量」，由 HC 自己聚合，
写记录的人不负责拆分。）

## 9. 按设计丢弃（HC 无对应类型）

| vivo 数据 | 出处 | 原因 |
|---|---|---|
| 睡眠评分 `SCORE` | `WATCH_SLEEP_BEAN` | HC 无睡眠评分类记录 |
| 呼吸质量 / 鼾声 / 呼吸暂停时长与风险 | 同表 `SLEEP_BREATHING_*`、`SNORE_*`、`APNOEA_*` | 同上（这些类型在 `RecordType` 里已标为废弃） |
| 血氧 `highAltitude` | `WATCH_OXYGEN` | HC 无海拔标记字段 |
| 运动配速 / 步频 / 步幅 / 泳姿分段 / GPS 轨迹 | `SPORT_RECORD_BY_WATCH_BEAN` 及其子表 | M4 只写会话本身；`ExerciseRoute` 涉及轨迹隐私，单独评估 |
| 体脂 | `WEIGHT_BEAN.BODY_FAT` | 实测为 0（未测），无有效数据 |
| 站立 / 中高强度分钟 | 日活动表 | HC 无对应类型 |

App 内会把这些列出来，不会静默丢弃。

## 10. 4 个决策点（已拍板）

### 决策点 1：「自由训练」→ **`STRENGTH_TRAINING` (70) 力量训练**（用户决定）

它是 47 条里最多的一类（18 条，占 38%），映射得好不好直接决定 HC 里运动数据的观感。

- A. `OTHER_WORKOUT` (0) —— 语义最保守，但在 HC 里只显示笼统的「其他训练」。~~我原本建议 A~~
- B. `STRENGTH_TRAINING` (70) —— **用户选这个**。手表上的自由训练主要用于器械/力量，
  显示成「力量训练」比「其他」更有信息量。

### 决策点 2：「仰卧起坐」→ **`CALISTHENICS` (13) 徒手健身**（用户决定）

仰卧起坐属于自重训练，语义贴近；不选 `STRENGTH_TRAINING` 是因为器械力量与徒手训练在 HC 里是两类。

### 决策点 3：午睡 → **全写**（用户决定）

- A. **全写** —— 数据真实存在，HC 也能正确聚合，用户在 HC 里能看到完整睡眠。
- B. 只写 ≥ 30 分钟 / C. 只写 ≥ 3 小时 —— 都会丢掉真实短睡。

依据：抽查显示短记录都是白天时段（13:07→13:53 这种），是真实午睡而非碎片误判；
HC 自己的睡眠视图会区分主睡眠与日间小睡。

### 决策点 4：身高 → **写**（用户决定）

`WEIGHT_BEAN.HEIGHT` 有值（cm），与体重同一时刻写一条 `HeightRecord`，HC 里身体信息完整。

> 附：`操场跑步`（TYPE 114）映射为 `RUNNING` 而非 `RUNNING_TREADMILL` ——
> 操场是跑道，不是跑步机。这一条由我在实现时纠正，已在代码注释里写明理由。

### 12.4 两个只在验收中才会发现的点

**① HC 库内基准单位与客户端单位不是一套。**

客户端传 `Energy.kilocalories` / `Mass.kilograms` / `Length.meters`，平台落库时换算成
**卡 / 克 / 米** 三个基准单位。所以库里看到 `energy=915650`、`weight=64000` 是对的，
不是我们写错。睡眠、心率这类无单位的类型不受影响。

**② 库内 `exercise_type` 是平台自己的 proto 序号，与客户端常量不是一套。**

客户端 SDK 走的是「常量 → 枚举名 → 平台」，见
`RecordToProtoConvertersKt.toProto` 里的 `enumValFromInt(exerciseType, EXERCISE_TYPE_INT_TO_STRING_MAP)`，
发出去的是**名字**，平台再按名字映射成自己的序号。实测对照表：

| 客户端常量 | 名字 | 库内 proto | vivo TYPE |
|---|---|---|---|
| 56 | `RUNNING` | 33 | 2 户外跑步、114 操场跑步 |
| 8 | `BIKING` | 4 | 4 户外骑行 |
| 74 | `SWIMMING_POOL` | 49 | 5 泳池游泳 |
| 70 | `STRENGTH_TRAINING` | 45 | 10 自由训练 |
| 79 | `WALKING` | 53 | 12 户外步行 |
| 26 | `EXERCISE_CLASS` | 11 | 13 健身课程 |
| 54 | `ROWING_MACHINE` | 61 | 20 划船机 |
| 2 | `BADMINTON` | 1 | 28 羽毛球 |
| 75 | `TABLE_TENNIS` | 50 | 30 乒乓球 |
| 13 | `CALISTHENICS` | 8 | 108 仰卧起坐 |

这层转换是 SDK/平台内部行为，我们只需保证名字对。验收时以**标题中文名**为准交叉验证 ——
11 种类型标题全部正确落库，反向证明映射链路无误。
